# 实机检查与验证记录

日期：2026-10-17 首轮验证，2026-10-19 更新并在 G30 安装验证。首轮配置 640×480；最新配置六路 1920×1080、30fps、H.264 CBR、每路 2Mbps，目标总计 12Mbps。下面旧记录保留历史背景，1080p 结果见后文。

## 已验证

- 原六路 C 采集源码使用项目私有 libuvc/libusb 依赖编译成功，板端 MPP JPEG 解码与 H.264 编码插件可用。
- 六台真实 `0bda:2292` 摄像头通过两组 Type-C Hub 同时枚举、采集和编码。
- 本次重启后两个 DWC3 控制器处于 Device，切到 Host 后恢复两组 Hub 和全部相机。该运行时初始化已加入 start.sh，并验证重复启动可用。
- **单个 HTTP/TCP 连接，板端 → 开发电脑**：约 10.625 秒同时取得六路各 300 个访问单元，每路均从关键帧开始，各收到 10 个关键帧，期间各路编码器重建增量均为 0。详见 http-capture.json。
- 将上述六路码流分别交给 FFmpeg 解码，每路均成功解码 300 帧，共 1800 帧；六路退出码均为 0，错误输出均为空。详见 http-decode.json。
- 板端最终状态快照六路 `source.online`、`transcode.online` 全为 true，采集与编码帧率约 30fps，详见 final-state.json。
- Python RTP 封装单元测试 2 项、实际 Android Java RTP 重组器互通测试 8 类曾通过；这些是保留的 G20 对照逻辑，当前 APP 固定 TCP，不使用 UDP。
- Android Debug APK 编译通过。APP 包名为 g30.sixcamera.app，与旧 K2 包名不同。

## 网络检查

eth0 为 192.168.144.10/24，协商 100Mbps 全双工、链路 up；192.168.144.11 可在 eth0 上解析为邻居。到 .11 的路由直接走 eth0，不经默认网关。eth1 的原默认路由保留。

用户确认专用光纤为 100M，并已开启光纤模式。最新实测 G30 的 eth0 到板端 eth0 直接通信，视频接口接收约 12.48Mbps、纯 TCP 接口接收约 95.55Mbps。较早 ar_net0 样本与最新 eth0 路径分开记录，详见带宽统计与实测.md。

## 2026-10-19 camera2 1080p 修复验证

- 原因：camera2 的输入 JPEG 被截断，旧逻辑只验开头，导致错误显示采集在线而编码没有输出。配置改为逐路 USB payload 1024/1024/3072/1536/1536/1536，并加入 JPEG 完整结构检查和残缺帧计数；详情见 camera2-1080p修复说明.md。
- 板端完成编译，JPEG 检查测试通过，覆盖填充、字节转义、重启标记、APP 内缩略图、截断、多个扫描段。
- 单个本地 TCP 连接同时取得六路各 300 帧，约 10.66 秒。FFprobe 确认六路实际编码尺寸全部为 1920×1080；FFmpeg 各解码 300 帧，共 1800 帧，全部退出码 0、错误输出为空，见 tcp-validation-1080p.json。此项验证采集/编码/码流，不单独证明光纤接收显示。
- 连续 120.37 秒、25 次状态采样六路持续在线；各路完整 JPEG 增量 3603～3604，编码增量 3610～3611，残缺帧、坏头、编码器重建增量全部 0，见 capture-stability-1080p.json。这只说明本观察窗口，没有宣称累计重建计数始终为 0。
- G30 现有 v1.1.0 APP 直接显示六路 1920×1080，约 30fps；camera2 放大及再次点击返回通过，最后停在六宫格。截图实收约 11.96Mbps、编码 12.08Mbps、重连 0、追帧 0。速率为短时显示读数，不能当光功率或丢包率。
- 修复后 final-state.json 六路 source/transcode 在线，incomplete_frames 全为 0；原 snappy-real 选定源码集合校验保持不变。旧 640×480 快照另存 final-state-640.json。
