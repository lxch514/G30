# 重新连接后的卡顿、重连排查与修复

2026-10-19。当前仍为六路 1920×1080、30fps、H.264 每路 2Mbps、单连接 TCP；未更改 APP、图传模式、网卡地址或旧 snappy-real。

## 原因和修改

现场 camera0 在原 USB 额度 1024 下，5 秒收到 150 帧，完整帧 0、残缺帧 150。监督进程判定采集停滞后约每十几秒重开全部六路，导致正常通道也周期性停顿。其他通道编码器重建累计约 18～19 次；G30 截图显示重连 47 次。

对当前接线，把 config/g30.json 的 payload_limits 从 [1024,1024,3072,1536,1536,1536] 改为 **[3072,1024,1024,1536,1536,1536]**。当前需要较大额度的是 camera0。此配置按 USB 排序编号分配，不能根据六台相同的序列号自动识别相机身份；换插口、相机或场景后需重新验证。不是把 USB 的额度当成 H.264 网络码率。

现场 board/g30_service.py 与之前验证版有两处功能差异：TCP feed 改成普通订阅，取消了队列积压时保留连接并逐路等新 IDR 的处理；状态接口也缺少 http_resyncs_total。已只恢复这两处功能，保留文件内其他现有内容。网络真正断开仍会正常重连；这里避免因可恢复的队列积压主动断开 TCP。

## 实测结果

- 六路各 300 帧、合计 1800 帧，实际编码尺寸均为 1920×1080，FFmpeg 解码全部成功、错误输出为空。
- 板端连续 120.40 秒采样，各路完整帧增量 3603～3604；残缺帧、坏头和编码器重建增量全部 0。
- G30 连续 123.17 秒、25 次 TCP 快照均包含同一条视频连接的客户端端口 46060；前后截图重连均为 0、追帧均为 0。观察期间可切换单路全屏，视频连接保持。
- G30 eth0 实测接口接收平均 12.55Mbps，收包错误和丢弃增量均为 0。该计数包含接口上的协议开销及其他流量，不是 APP 净荷或链路容量。
- 之后状态快照每路已累计编码约 1.9 万帧（约 10 分钟），六路在线、约 30fps、残缺帧累计 0。编码器重建计数为启动时的 1，观察期间没有继续增长。
- 当前板端 eth0 100M 全双工，G30 到板端 .10 路由为 eth0。没有发现网口收发错误；不据此推断光功率衰减为零。

内核历史日志中有 Hub 重新枚举以及零星 xHCI 内存访问不及时告警；本次修复后未观察到新的物理 USB 断开，采样/解码检查通过。这里是当前接线和场景的短时验证，不代表任意接线或长期工况都已经验收。

## 当前版本和文件

板端 /root/G30 是已运行的修复版本，dist/G30-project.zip 同步为当前源码。APP 无需重装。程序本身不创建自动历史备份。

用户要求板端只保留当前程序，本次已删除 /root/G30/backups；电脑上之前保存的归档保留。上午修复记录中的旧板端备份路径现已不存在，请以本说明和当前配置为准。

当前接线请保持两个 Hub 与摄像头的物理插口位置。若以后交换插口，先检查各路 incomplete_frames、captured_fps 和编码重建增量；不要直接通过调高网络码率来处理 USB 输入残缺。
