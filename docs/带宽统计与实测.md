# 顶部带宽统计与实测

实测日期：2026-10-19。下面带宽/容量测量使用 G30 APP v1.1.0、640×480/30fps、六路 H.264、每路目标 2Mbps。后续项目已改为 1920×1080/30fps，仍为每路 2Mbps；最新 G30 截图实收约 11.96Mbps、编码 12.08Mbps。下面纯 TCP 容量测试没有因改分辨率而重复，历史测量条件保留。

## 当前实测结果

| 项目 | 结果 | 统计范围 |
|---|---:|---|
| 六路视频净荷接收 | 约 12.0Mbps | APP 实际读到的 H.264 字节，近 5 秒均值 |
| 图传接口视频期间接收 | 12.48Mbps | G30 eth0 接收字节，20.672 秒均值，含协议与其他接口流量 |
| 纯 TCP RAM 发送 | 94.57Mbps | 板端向 G30 写入的随机数据；约 6 秒，不经过摄像头和解码器 |
| 纯 TCP 接口接收 | 95.55Mbps | G30 eth0 接收字节，约 6.156 秒，含协议开销 |

纯 TCP 探测时暂停监控 APP，测试完立即恢复；一次性探测服务自动退出，不常驻监听。板端 eth0 协商 100Mbps 全双工。此次结果接近百兆链路的可用吞吐，但不是长期可靠性、BER 或光功率测量。

用户确认开启光纤模式。较早样本中，G30 到 192.168.144.10 的路由走 ar_net0，视频期间接口流量约 7.45Mbps。最新测试时该路由已切到 eth0，视频恢复约 12Mbps、六路约 30fps，短时测试中重连与追帧均为 0。没有把 ar_net0 的旧样本当作当前 eth0 光纤链路的能力结论，也没有通过程序更改 G30 路由或图传模式。

## 界面字段

- **接收(5s)**：六路 H.264 净荷字节增量 × 8 ÷ 采样秒数 ÷ 1,000,000。每秒刷新，约 5 秒窗口平滑；连接刚启动时使用已积累的采样时间。不是将配置码率直接显示出来，不包含 16 字节封装头、TCP/IP、链路层或重传开销。
- **编码**：板端六路当前实际编码速率之和。板端与 APP 的窗口并非完全同步，短时间的小幅差异正常。
- **响应**：一次状态 HTTP 请求的完整耗时，包含建连、板端处理、传输与 JSON 读取；不是纯网络 RTT，也不是画面端到端延迟。
- **重连**：当前 APP 连接期间额外发起 TCP 连接的次数；停止/重新打开 APP 或保存连接设置后重新计数。
- **追帧**：本轮板端服务中，所有 TCP 订阅队列积压后清空过期内容、重新等各路 IDR 的累计次数。不是 TCP 重传次数、丢包率或光功率衰减；重启板端 H.264 服务后归零。
- **各画面底部 Mbps/fps**：该路实际收到的 H.264 字节速率与解码输出帧率。

稳定连接超过 8 秒，若近 5 秒接收低于当前编码的 80%，顶部显示黄色“接收不足”。没有新视频超过约 1.8 秒时显示等待或无视频时长；状态数据过期时不继续显示旧的编码速率。

## 如何解读

当前每路 2M，六路视频应在约 12Mbps 附近。若接收长时间低于编码，且追帧/重连增加、帧率下降，应检查当前路径和数据转发能力。若板端相机或编码状态本身离线，应先检查采集与服务。接收速率正常而显示帧率低，则还应检查解码和渲染负载。

TCP 会重传，不能根据两侧码率差计算链路丢包率，更不能换算成 dBm 或光纤衰减百分比。要看光功率，需要光模块诊断数据或光功率计。本项目没有读到或虚构这类数值。

## 复查路径

```bat
adb -s 1234567 shell ip route get 192.168.144.10
```

当前实测为 G30 `192.168.144.11` 经 eth0 到板端 `192.168.144.10`。设备序列号若变化，以 `adb devices` 为准。板端与 G30 同为 /24，直连不需要替换板端默认网关。

每路 6M/8M 的目标总量分别是 36/48Mbps，另有协议开销；配置已支持，本次没有将它们当作已经完成的六路现场测试。
